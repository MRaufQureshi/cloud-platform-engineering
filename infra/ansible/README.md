# ansible

Configuration management for the private EC2 in `infra/core`. Terraform builds
the server; Ansible installs and configures what runs on it.

---

## Run it

**Before anything:** the private instance sits in a subnet with no internet
route. Ansible installs packages from the internet, so uncomment the NAT
Gateway block in [`infra/core/network_provisioning.tf`](../core/network_provisioning.tf)
and `terraform apply` first. Without it every install task fails.
See [PREREQUISITES.md §9](../../PREREQUISITES.md).

```bash
# 1. core generates the inventory for you
cd infra/core && terraform apply

# 2. set the database password
cd ../ansible
cp inventory/group_vars/database_servers.yml.example \
   inventory/group_vars/database_servers.yml
#    edit it — app_db_password has no default anywhere

# 3. check Ansible can reach the host
ansible database_servers -m ping

# 4. install and configure MariaDB
ansible-playbook playbooks/site.yml
```

`ping` should return `pong`. If it doesn't, stop there — every playbook below
fails the same way.

### Verify

```bash
ansible database_servers -m shell -a "systemctl status mariadb" --become
ansible database_servers -m shell -a "cat /etc/my.cnf.d/ansible.cnf" --become
```

### Teardown

Nothing to undo. Ansible changed a server; `terraform destroy` in `infra/core`
deletes the server.

## What you'll learn

- **Push-based configuration management** — one control node, no agent installed
  on the target
- **Inventory as a generated artifact** — Terraform writes it, you never copy an
  IP by hand
- **Roles** — the refactor from one long playbook into a reusable unit
- **Handlers and templates** — restart a service only when its config actually
  changed
- **Variable precedence** — why `defaults/` is the weakest place to set a value

## What each file does

```
ansible.cfg                        where to find the inventory and the roles
playbooks/
  site.yml                         ← the one you run. calls the role.
  install_mysql.yml                earlier step: install, as a flat playbook
  configure_mysql.yml              earlier step: database + user, flat
inventory/
  hosts.ini                        GENERATED by terraform. gitignored.
  group_vars/database_servers.yml  the password. gitignored.
roles/mysql/
  tasks/main.yml                   what to do
  defaults/main.yml                fallback values, lowest precedence
  handlers/main.yml                restart MariaDB, only when notified
  templates/my-ansible.cnf.j2      the config file, with variables in it
requirements.yml                   the collection this needs
```

### Three playbooks, one lesson

`site.yml` is what you run. The other two are the same work before it was
refactored into a role — kept on purpose, because the progression is the point:

| | |
|---|---|
| `install_mysql.yml` | install the package, start the service |
| `configure_mysql.yml` | add the database and the application user |
| `roles/mysql` + `site.yml` | the two above, refactored into a reusable role |

A role is a fixed folder layout Ansible knows how to load. Point `site.yml` at
`mysql` and `tasks/`, `defaults/`, `handlers/` and `templates/` are all picked
up without being named. That convention is what makes the role droppable into
another project.

### Where the password comes from

```
roles/mysql/defaults/main.yml               lowest precedence — no password here
inventory/group_vars/database_servers.yml   wins. gitignored.
```

Ansible loads `group_vars/<name>.yml` automatically when `<name>` matches a
group in the inventory — here, `[database_servers]`. `defaults/` is named
*defaults* for a reason: it is the weakest source of a value, so it holds the
things that rarely change and none of the things that are secret.

Leaving `app_db_password` undefined in both files is deliberate. The run fails
loudly instead of quietly shipping a weak password.

> Real projects encrypt this with `ansible-vault encrypt`, which lets the file
> stay in git. Gitignoring it is the simpler equivalent.

### How Ansible reaches a server with no public IP

```
your laptop ──▶ EC2 Instance Connect Endpoint ──▶ private EC2
                (IAM-authorized tunnel)            no public IP
```

`infra/core/ansible_inventory.tf` writes the connection string into `hosts.ini`
on every apply. The tunnel is an `ssh -o ProxyCommand=...` that runs
`aws ec2-instance-connect open-tunnel` — SSH connects *through* that command's
output instead of opening a socket itself.

Needs AWS CLI ≥ 2.12 and `ec2-instance-connect:OpenTunnel` in your IAM.

> The older way is a bastion: a public EC2 you SSH into first and hop from. It
> works, and that line is kept commented in `ansible_inventory.tf`, but it means
> running a public host you have to patch and keeping port 22 open to the
> internet. The endpoint has neither.

## Collections

The modules used here (`community.mysql`) ship with the full `ansible` package:

```bash
brew install ansible
```

If you installed `ansible-core` instead, you have none of them:

```bash
ansible-galaxy collection install -r requirements.yml
```

> `playbooks/configure_mysql.yml` calls the same modules under the newer
> `ansible.mysql` namespace. Both are valid and both ship in the `ansible`
> package — a useful thing to have seen once.

## If `ping` fails

| | |
|---|---|
| `Permission denied (publickey)` | `chmod 400 ~/.ssh/your-key-pair.pem` |
| Key still refused | `ssh-add -D && ssh-add ~/.ssh/your-key-pair.pem` |
| `open-tunnel: command not found` | AWS CLI is older than 2.12 |
| `UnauthorizedOperation` on the tunnel | your IAM is missing `ec2-instance-connect:OpenTunnel` |
| Connects, but every install task fails | the NAT Gateway is still commented out |

Finding a package's real name on the target, which is usually what blocks a
first run:

```bash
ansible database_servers -m shell -a "dnf search mysql | grep -i server"
```
